# `GAME_OVER` 상태를 없애는 게 맞는가 — 판단

> 브랜치 `claude/death-hint-gamestate`
> 결론: **없애는 게 맞다. 없앴다.** 이유는 취향이 아니라 기계적인 것이다.

---

## 1. 지금 `GAME_OVER`는 무엇이었나

코드 전체에서 세 군데에만 등장했다.

| 위치 | 내용 |
|---|---|
| `GameManager.gd:5` | enum 멤버 선언 |
| `InputManager.gd:82` | `match` 분기 → `pass` |
| **설정하는 곳** | **0곳** |

`set_state(GAME_OVER)`를 호출하는 코드가 없다. 즉 **이 상태는 한 번도 진입하지 않는다.**
제거해도 동작이 바뀌는 지점이 존재하지 않는다 (enum 멤버 하나 + `pass` 분기 하나 삭제).

---

## 2. 결정적인 이유: 썼다면 이번 기능이 깨진다

`GAME_OVER`를 **실제로 쓰기 시작하면** "더블 탭으로 되돌리기" 안내가 거짓말이 된다.

```gdscript
# InputManager.check_input
if GameManager.cur_state != GameManager.GameState.PLAYING:
    _reset_touch()
    _cancel_pending_tap()      # ← 매 이벤트마다 대기 중인 첫 탭을 버린다
```

더블 탭은 **첫 탭을 기억해 두고 두 번째 탭을 기다리는** 방식이다(`_pending_tap`).
PLAYING이 아닌 상태에서는 위 가드가 **들어오는 이벤트마다 그 기억을 지운다.**
그래서 `GAME_OVER`에서는 더블 탭이 **원리적으로 성립하지 않는다.**
게다가 `match`의 `GAME_OVER` 분기는 `pass`라 제스처 처리 자체가 아예 돌지 않는다.

→ `GAME_OVER`를 쓰면서 되돌리기를 살리려면 **PLAYING의 터치 파이프라인을
두 번째 상태에 복제**해야 한다. 기능 하나 얻으려고 입력 코드를 이중화하는 것이다.

---

## 3. 구조적인 이유: `GameState`가 답하는 질문이 다르다

`GameState`가 답하는 질문은 **"지금 어떤 입력 체계인가"**다.

| 상태 | 입력 체계 |
|---|---|
| `MAIN_MENU` | 아무 키나 누르면 넘어감 |
| `TIP` | 아무 키나 누르면 닫힘 |
| `PLAYING` | 스와이프=이동 / 롱프레스=상호작용 / 더블탭=되돌리기 |

죽음은 **입력 체계를 바꾸지 않는다.** 죽어도 스와이프·탭·더블탭의 의미는 그대로다.
단지 **이동이 합법적인 수가 아니게** 될 뿐이다. 그건 이미 올바른 곳에서 처리하고 있다.

```gdscript
# ActionManager
func _on_action_input(dir):              # 이동
    if player.is_dead or player.is_fallen: return   # ← 막는다

func _on_back_input():                   # 되돌리기
    ...                                   # ← 막지 않는다
```

**이게 정확히 맞는 설계다.** 생사는 `Unit.is_dead` / `is_fallen`으로 **개체 단위**에 있고,
되돌리기는 열어 두고 이동만 닫는다. 여기에 전역 상태를 하나 더 얹으면
**같은 사실의 출처가 둘**이 된다. 그리고 그 둘은 반드시 어긋난다 —
되돌리기가 `is_dead`를 false로 복원할 때 전역 상태는 누가 되돌리는가?

> 정정: 이전 QA 리포트에 "죽으면 입력이 전부 막힌다"고 적었는데 **틀렸다.**
> 막히는 것은 이동뿐이고 되돌리기는 처음부터 살아 있었다. 문제는 입력이 아니라
> **되돌릴 수 있다는 사실을 아무도 알려주지 않는 것**이었다. 그래서 고칠 것은
> 상태 머신이 아니라 **안내 UI** 하나다.

## 4. 반대 논거와 그 반박

**"전역 상태가 있으면 다른 시스템(BGM·UI)이 반응하기 쉽다"**
→ 이미 반응하고 있다. `Player._anim_died`가 BGM을 멈추고, `_undo_anim_died`가 되살린다.
개체의 연출 훅으로 충분하며, 전역 상태보다 **턴 파이프라인과 타이밍이 정확히 맞는다.**

**"나중에 진짜 게임오버가 필요해지면?"**
→ 그때 다시 넣으면 된다. enum 멤버 한 줄이다. 쓰지 않는 상태를 미리 두는 비용은
"이 상태는 뭐지, 언제 들어가지?"를 읽는 사람이 매번 확인해야 하는 것이고,
실제로 이번에 그 확인을 하느라 세 파일을 추적했다.

## 5. 그래서 무엇을 했나

**제거**
- `GameManager.GameState`에서 `GAME_OVER` 삭제 + enum이 무엇을 담는 그릇인지 주석으로 고정
- `InputManager.check_input`의 죽은 `match` 분기 삭제

**대체 (안내 UI)**
- `01_Scripts/UI/DeathHint.gd` + `main.tscn`의 `UI/InGame/DeathHint` 라벨
- 전역 상태를 **건드리지 않는다.** 플레이어의 `is_dead` / `is_fallen`만 본다
- 입력 체계가 PLAYING에 머물러 있으므로 더블 탭 되돌리기가 그대로 동작한다

**곁가지로 발견해 고친 버그**
- `Unit.died()`가 `undo_action` 없이 기록해 `_undo_anim_died`가 **영구히 호출되지 않았다.**
  → 체력 사망을 되돌리면 BGM이 다시 멈춘 채로 남는다. 낙하 쪽에서 고친 것과 같은 계열의
  버그가 사망 쪽에도 있었던 것. `record_new(..., "died", {}, "undo_died", {})`로 수정
- `GameManager.set_state`의 디버그 `print`가 `{...}` 보간을 쓰고 있어(GDScript에 없는 문법)
  리터럴 중괄호를 출력하고 있었다. 변수명도 `GameSate`로 오타. `%` 포맷으로 수정

## 6. 안내 UI 동작 규칙

| 조건 | 동작 |
|---|---|
| 턴이 끝났고 플레이어가 죽거나 떨어졌고 되돌릴 기록이 있다 | **1초 뒤** 알파 0→1 (0.3초) |
| 되돌리기로 살아났다 | 알파 1→0 (0.2초) |
| 리셋 / 홈 / 월드 이동 | 같음 (스테이지 로드 경로) |
| 죽었는데 되돌릴 기록이 없다 | **띄우지 않는다** — 거짓 안내가 되므로 |

판정은 `_refresh()` **한 곳**에서만 한다. 띄우는 조건과 지우는 조건을 따로 두면
반드시 어긋나기 때문에, "지금 안내가 필요한가"를 매번 새로 계산하고 그 결과에 맞춘다.

구독하는 신호 두 개를 새로 추가했다.
- `ActionManager.turn_finished` — 정방향 턴과 되돌리기 턴 양쪽 종료 후
- `StageDirector.stage_loaded` — 리셋·홈·월드 이동이 모두 지나는 공통 경로

`UndoManager.has_history()`도 추가했다(기존 `_history`는 private).

## 7. 남은 판단거리

- **설정창을 열면 안내가 Dim 아래로 비친다.** 가릴지 말지는 취향이라 그대로 뒀다
- **스폰 즉시 사망**(시작 칸 고추 피해 ≥ 시작 체력)은 되돌릴 기록이 없어 안내가 안 뜬다.
  현재 그런 스테이지는 없고, 있다면 **레벨 디자인 오류**(시작부터 사망)다
- **텍스트가 영어**(`double tap to undo`)다. 현재 폰트에 한글 글리프가 없어
  한글화는 폰트 교체가 선행돼야 한다 (`docs/07` B-4)
